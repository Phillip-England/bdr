bdr in one sentence

bdr lets you write small text scripts that drive a real browser with Playwright and, when needed, control the real desktop with system mouse and keyboard primitives.

The project is designed around a constrained DSL rather than arbitrary Python. The tradeoff is deliberate: fewer moving parts in exchange for clearer scripts, easier validation, and better error messages.

# login.bdr
$url = "https://example.com/login"

load($url)
#email.fill("me@example.com")
#password.fill("hunter2")
#submit.click()
assert_title("Dashboard")
screenshot("done.png")

Install

bdr uses uv for dependency management and Playwright for browser automation.

make dev
uv run bdr setup
Desktop input is powered by pyautogui. Those commands need a real GUI session and may require OS permissions. On macOS, expect Accessibility and Screen Recording prompts.

Mental Model

There are three layers in the language:

  • Page commands such as load(), wait(), and assert_title().
  • Element chains such as #email.fill("me@example.com") or .item[0].click().
  • Desktop commands and helper expressions for operating-system level automation.

Scripts are plain text, line oriented, and intentionally simple. Variables are global to the current run. Functions are reusable blocks with positional parameters. exec() inlines another script into the current session.

Variables require the $ prefix. Settings do not.

Browser keyboard and scrolling

press() sends keys through Playwright to the active page.

press("Enter")
press("Tab")
scroll_up()
scroll_down()

Useful element actions

Action Purpose
.click()Click a single matched element.
.fill()Clear then fill an input or textarea.
.type()Type character by character.
.select()Select a dropdown option by visible label.
.upload()Attach local files to a file input.
.draw()Draw on a canvas or signature pad.
.scroll_to()Bring an element into view.

Desktop Input

Desktop commands operate on the real mouse, keyboard, and screen. Use them for native dialogs, browser chrome, or visual workflows where DOM selectors are not enough.

mouse_move(400, 300)
mouse_move(400, 300, 0.2)
mouse_move_by(50, 0)
mouse_move_point("640,360")

mouse_click()
mouse_click("right")
mouse_click("left", 2)

mouse_drag_to(900, 600, 0.4)
mouse_drag_by(120, 0, 0.2)
mouse_scroll(-300)

key_press("enter")
key_down("shift")
key_up("shift")
hotkey("command", "l")
type_text("https://example.com")
type_text("slow text", 0.03)
Important: press() is browser-level Playwright input. key_press() is operating-system level input. They are intentionally separate because they affect different targets.

Built-in Helpers

Helpers return values that can be assigned to variables or passed into commands. Points are represented as "x,y". Colors are represented as "r,g,b".

Helper Result
point(x, y)Build a point string.
offset_point(point, dx, dy)Apply a relative offset to a point.
mouse_point()Current mouse position.
mouse_x() / mouse_y()Current mouse coordinates.
screen_width() / screen_height()Current screen dimensions.
screen_size()Screen size as a point string.
screen_center()Center point of the current screen.
pixel_color(x, y)RGB value for a pixel.
nearest_color_point(r, g, b, tolerance?, radius?)Closest matching pixel from the current mouse position.
nearest_color_point_from(x, y, r, g, b, tolerance?, radius?)Closest matching pixel from an explicit origin.

Examples

$center = screen_center()
$right = offset_point($center, 50, 0)
mouse_move_point($right, 0.2)

$color = pixel_color(mouse_x(), mouse_y())
log("mouse color", $color)

$target = nearest_color_point(255, 0, 0, 12)
mouse_move_point($target, 0.2)
mouse_click()

nearest_color_point(255, 0, 0, 12) means “find the closest pixel to the current cursor whose RGB value is close to pure red, allowing up to 12 points of difference per channel.”

Functions

Functions are reusable command blocks. They take positional arguments and do not return values.

func login($user, $pass) {
  #email.fill($user)
  #password.fill($pass)
  #submit.click()
}

load("https://example.com/login")
login("me@example.com", "hunter2")

Function bodies can use browser commands, element chains, and desktop commands. Parameter bindings are local to the function call.

Random Data

bdr ships with random_* generators for common test-data needs.

$email = random_email()
$pass = random_password(16)
$phone = random_phone()
$country = random_country()

These work in assignments and direct command arguments.

Project Layout

examples/
  login.bdr
  functions.bdr
  desktop-input.bdr

bdr/
  cli.py
  lexer.py
  interpreter.py
  runner.py
  input.py

lexer.py tokenizes the DSL. runner.py validates and launches scripts. interpreter.py executes commands. input.py contains the desktop-input adapter and screen helper logic.

Examples

DOM-first browser flow

load("https://www.wikipedia.org")
[name="search"].fill("Playwright")
press("Enter")
assert_title("Playwright")

Desktop-first visual flow

$target = nearest_color_point(255, 0, 0, 12)
mouse_move_point($target, 0.2)
mouse_click()
mouse_move_by(50, 0, 0.1)

Mixed workflow

load("https://example.com")
#upload.click()
mouse_move(700, 480)
mouse_click()
type_text("/Users/me/Desktop/file.pdf")
key_press("enter")

The mixed style is the main reason the project now has both Playwright-native commands and desktop-native commands. Many real automations need both.
